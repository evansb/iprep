# 7. Moves and Copies

C++ copies values unless an object can be constructed in place or its resources can be transferred. Knowing which case applies turns invisible allocations into predictable operations and makes ownership explicit. It also answers an interview staple: `std::move` moves nothing by itself.

## Copies, and where they hide

Copy construction creates a new object from an existing object. Copy assignment replaces the value of an object that already exists.

```cpp
struct T {
    T(const T& other);             // copy constructor
    T& operator=(const T& other);  // copy-assignment operator
};
```

When these functions are generated by the compiler, they copy each base and non-static data member. That memberwise operation is correct for value-like members such as `std::string` and `std::vector`, which define their own deep-copy behavior. It is usually wrong for a raw handle that represents unique ownership, as Chapter 4's special-member rules established.

Copies do not need explicit spelling:

```cpp
#include <iostream>
#include <string>

struct Snapshot {
    std::string symbol;

    explicit Snapshot(const char* value) : symbol(value) {}

    Snapshot(const Snapshot& other) : symbol(other.symbol) {
        std::cout << "copy-ctor\n";
    }

    Snapshot& operator=(const Snapshot& other) {
        symbol = other.symbol;
        std::cout << "copy-assign\n";
        return *this;
    }
};

void inspect_value(Snapshot snapshot) {
    std::cout << snapshot.symbol << '\n';
}

void inspect_reference(const Snapshot& snapshot) {
    std::cout << snapshot.symbol << '\n';
}

int main() {
    Snapshot first{"EURUSD"};
    Snapshot second = first;  // prints: copy-ctor
    second = first;           // prints: copy-assign
    inspect_value(first);     // prints: copy-ctor, then EURUSD
    inspect_reference(first); // prints: EURUSD
}
```

A by-value parameter needs its own object. A `const` reference aliases the caller's object, so `inspect_reference` constructs nothing.

Returning values, inserting elements into containers, and growing containers can also invoke copies. Elision changes the return case later in this chapter; Chapter 10 examines container growth.

A copy of a resource-owning value duplicates that resource. Copying a `std::vector<double>` allocates storage for the destination and copies every element. The source and destination are then independent.

**Pitfall.** A heavy type passed by value pays a silent-copy tax when the caller supplies an lvalue. Use `const T&` for read-only access, or deliberately accept by value when the function needs to consume or retain a value.

Type deduction can hide the same difference:

```cpp
std::vector<double> prices{101.0, 101.5};

auto copied = prices;          // copies the vector and its elements
auto& aliased = prices;        // no copy
const auto& read_only = prices; // no copy
```

## Move semantics: transfer, not teleportation

A move transfers an owned resource into another object. For a heap-backed vector, the difference is structural:

```text
copy
source: [data*] ──> [ e0 e1 ... eN ]
target: [data*] ──> [ e0 e1 ... eN ]  new allocation, N element copies

move
source: [valid, unspecified state]
target: [data*, size, capacity] ──────> [ e0 e1 ... eN ]
                                      ownership of existing allocation
```

Move construction creates an object from an expiring object. Move assignment first disposes of the destination's current resource, then takes the source's resource.

```cpp
struct T {
    T(T&& other);             // move constructor
    T& operator=(T&& other);  // move-assignment operator
};
```

The `&&` makes the parameter an rvalue reference. It can bind to an object whose resources may be taken. A hand-written owner shows the required pattern:

```cpp
class Buffer {
public:
    explicit Buffer(std::size_t size)
        : data_(new double[size]{}), size_(size) {}

    ~Buffer() {
        delete[] data_;
    }

    Buffer(const Buffer&) = delete;
    Buffer& operator=(const Buffer&) = delete;

    Buffer(Buffer&& other) noexcept
        : data_(std::exchange(other.data_, nullptr)),
          size_(std::exchange(other.size_, 0)) {
        std::cout << "move-ctor\n";
    }

    Buffer& operator=(Buffer&& other) noexcept {
        if (this != &other) {
            delete[] data_;
            data_ = std::exchange(other.data_, nullptr);
            size_ = std::exchange(other.size_, 0);
        }
        std::cout << "move-assign\n";
        return *this;
    }

    bool empty() const {
        return size_ == 0;
    }

private:
    double* data_;
    std::size_t size_;
};

int main() {
    Buffer first{1'024};
    Buffer second = std::move(first);  // prints: move-ctor
    std::cout << first.empty() << '\n'; // prints: 1
}
```

`std::exchange` returns the old member value while replacing it. Nulling `other.data_` prevents its destructor from deleting the allocation now owned by the destination. The self-check in move assignment prevents `buffer = std::move(buffer)` from deleting the resource before trying to take it.

| `std::vector<double>` operation | Allocations | Element operations | Source afterward |
|---|---:|---:|---|
| Copy construction | One for destination | Copy `N` elements | Unchanged |
| Move construction | Normally none | Normally none | Valid, value unspecified |

Allocator details can alter a container's move costs in specialized code, but the ordinary move constructor transfers the allocation.

Moving an `int` still copies its bits; it has no external resource to steal. Move semantics help when a type owns storage, an operating-system handle, or another resource represented indirectly.

**Pitfall.** Failing to empty the source of a hand-written move leaves two owners. Both destructors then release the same resource, causing undefined behavior.

## Value categories and move eligibility

The value categories from Chapter 3 now determine which constructor overload wins:

| Category | Typical expression | Ownership behavior |
|---|---|---|
| lvalue | Named object `order` | Copies unless explicitly cast |
| prvalue | Temporary `Order{42}` | Usually initializes directly |
| xvalue | `std::move(order)` | Can bind to a move overload |

An xvalue is an “expiring value”: it identifies an object whose resources may be reused. `std::move(x)` produces an xvalue. A named local in a return statement is move-eligible automatically if elision does not happen.

Overload resolution makes the choice visible:

```cpp
struct Order {};

void sink(const Order&) {
    std::cout << "lvalue\n";
}

void sink(Order&&) {
    std::cout << "rvalue\n";
}

void relay(Order&& order) {
    sink(order);            // prints: lvalue
    sink(std::move(order)); // prints: rvalue
}

int main() {
    Order order;
    sink(order);            // prints: lvalue
    sink(Order{});          // prints: rvalue
    sink(std::move(order)); // prints: rvalue
}
```

A variable expression is an lvalue even when the variable's declared type is `Order&&`. The name `order` gives repeated access to a particular object; `std::move(order)` explicitly marks the point where `relay` passes that object's value onward.

**Rule.** A named rvalue reference is an lvalue. Apply `std::move` when that function intentionally transfers ownership onward.

## std::move and std::forward

`std::move` is a cast, conceptually a `static_cast<T&&>`. It performs no transfer and generates no instructions. It changes the expression's value category so overload resolution may select a move constructor or move assignment operator.

```cpp
std::string first = "EURUSD";
auto second = std::move(first);
// std::move itself compiles to zero instructions.
// The selected move constructor does the work; verify in Compiler Explorer (Chapter 1).
```

The request can be refused. Move constructors conventionally take `T&&`, which cannot bind to a `const T` object because moving usually modifies the source. A `const` source therefore selects a copy constructor taking `const T&`:

```cpp
struct Order {
    Order() = default;

    Order(const Order&) {
        std::cout << "copy-ctor\n";
    }

    Order(Order&&) noexcept {
        std::cout << "move-ctor\n";
    }
};

const Order original;
auto copy = std::move(original); // prints: copy-ctor
```

The same fallback occurs when a type has no usable move operation but does have a copy operation. `std::move` has still produced an xvalue; the best viable overload merely happens to be the copy.

**Pitfall.** Do not add `const` to an object that must transfer ownership. `std::move` preserves `const`, producing `const T&&`, not `T&&`.

`std::forward` solves a narrower problem. In template code, it preserves the caller's value category so a wrapped argument moves if and only if the caller supplied an rvalue. Its forwarding-reference and reference-collapsing machinery belongs in Chapter 20.

## Moved-from objects

A moved-from standard-library object is valid but has an unspecified value unless that type documents a stronger guarantee. Its invariants still hold, but the standard does not tell you which ordinary value it contains. User-defined types should provide the same baseline guarantee.

```cpp
void reuse_after_move() {
    std::string symbol = "EURUSD";
    std::string destination = std::move(symbol);

    std::cout << destination << '\n'; // prints: EURUSD
    std::cout << symbol << '\n';      // valid, but output is unspecified

    symbol = "USDJPY";                 // establish a fresh, known value
    std::cout << symbol << '\n';       // prints: USDJPY
}
```

Implementations commonly leave a moved-from string empty. Code that relies on that observation is not portable.

| Operation on a moved-from standard object | Allowed? |
|---|---|
| Destroy it | Yes |
| Assign a new value | Yes |
| Call an operation without preconditions, such as `clear()` | Yes |
| Read its value | Valid, but result unspecified |
| Rely on `empty()` being `true` | No |

**Rule.** A moved-from object must be destructible and assignable; assume nothing else unless its type states a stronger postcondition.

A moved-from object is not destroyed. Its destructor still runs at the end of its lifetime, which is why a resource-owning move must leave the source safe to destroy (Chapter 5).

Clang-Tidy diagnoses many accidental reads after a move:

```sh
clang-tidy order.cpp -checks=-*,bugprone-use-after-move -- \
    -std=c++23
```

The analysis is conservative rather than a language rule, but it catches the common pattern where a name is used again before receiving a new value.

## Elision: RVO, NRVO, and guaranteed elision

Copy elision means constructing a result directly in its final storage instead of first creating an object that must be copied or moved. The prvalue return case is traditionally called return value optimization, or RVO. Guaranteed copy elision (C++17) means returning a prvalue of the function's result type performs this direct construction:

```cpp
struct Order {
    explicit Order(int) {}
    Order(const Order&) = delete;
    Order(Order&&) = delete;
};

Order make_direct(int id) {
    return Order{id}; // guaranteed elision: no copy or move
}
```

No temporary `Order` needs to exist separately from the caller's result object. This is guaranteed even if `Order` declares neither a copy nor a move constructor; temporary materialization from Chapter 5 supplies an object only where one is needed.

Named return value optimization, or NRVO, is different. A compiler is permitted to construct a named local directly in the return destination, and production compilers usually do so for a straightforward local. If NRVO does not happen, the return expression is move-eligible and invokes the move constructor.

```cpp
struct Order {
    int id;

    explicit Order(int value) : id(value) {
        std::cout << "ctor\n";
    }

    Order(const Order& other) : id(other.id) {
        std::cout << "copy-ctor\n";
    }

    Order(Order&& other) noexcept : id(other.id) {
        std::cout << "move-ctor\n";
    }
};

Order make_prvalue() {
    return Order{1};          // ctor only; guaranteed
}

Order make_local() {
    Order order{2};
    return order;             // usually ctor only; otherwise move-ctor
}

Order force_move() {
    Order order{3};
    return std::move(order);  // ctor, then move-ctor
}

Order return_parameter(Order order) {
    return order;             // move-ctor; a parameter cannot use NRVO
}
```

Guaranteed elision is a language rule, not an optimization-level choice: `-O0` does not restore the missing move in `make_prvalue`. NRVO remains optional and can be disabled by compiler options intended for investigation.

| Return statement | What happens | Notes |
|---|---|---|
| `return Order{1};` | Guaranteed direct construction | Since C++17 |
| `return local;` | NRVO, otherwise implicit move | Named local of result type |
| `return std::move(local);` | Move | Prevents NRVO |
| `return parameter;` | Implicit move | Parameters cannot use NRVO |
| `return local.member;` | Copy unless explicitly moved | Subobjects cannot use NRVO |

**Pitfall.** `return std::move(local);` is usually a pessimization. It changes an NRVO candidate into an xvalue, forcing a move where direct construction was possible.

Multiple divergent named return objects can prevent NRVO:

```cpp
Order choose(bool primary) {
    Order first{1};
    Order second{2};
    return primary ? first : second; // copy: conditional expression is an lvalue
}
```

Prefer a prvalue expression when the alternatives naturally construct distinct results. Do not contort clear code solely to chase optional NRVO; first remove explicit `std::move` from ordinary local returns.

## Move-only types and defaulting rules

Some resources are inherently unique. Two objects cannot independently own the same connected socket, open file, or lock, so copying the owner is meaningless. Delete copying and support transfer:

```cpp
class Socket {
public:
    explicit Socket(int fd) : fd_(fd) {}

    ~Socket() {
        if (fd_ >= 0) {
            ::close(fd_);
        }
    }

    Socket(const Socket&) = delete;
    Socket& operator=(const Socket&) = delete;

    Socket(Socket&& other) noexcept
        : fd_(std::exchange(other.fd_, -1)) {}

    Socket& operator=(Socket&& other) noexcept {
        if (this != &other) {
            if (fd_ >= 0) {
                ::close(fd_);
            }
            fd_ = std::exchange(other.fd_, -1);
        }
        return *this;
    }

private:
    int fd_;
};

void consume(Socket socket) {
    // socket owns the connection
    (void)socket;
}

int open_connection();

void hand_off() {
    Socket connection{open_connection()};
    consume(std::move(connection)); // ownership enters consume
}
```

Assume `open_connection` returns an operating-system file descriptor. The scalar `int` itself does not implement ownership, so defaulted moves would merely copy it and both objects would close the same descriptor. A direct resource owner must write the transfer. Once ownership lives in a suitable member type, the enclosing class should default its moves—or, preferably, declare none of the five special members. The move-only owner used in ordinary application code is `std::unique_ptr` (Chapter 8).

A user-declared destructor or copy operation suppresses implicit move generation, as the Chapter 4 matrix showed. The result may silently copy:

```cpp
struct Trace {
    Trace() = default;
    Trace(const Trace&) {
        std::cout << "member copy\n";
    }
    Trace(Trace&&) noexcept {
        std::cout << "member move\n";
    }
};

struct Widget {
    Trace trace;
    ~Widget() {
        std::cout << "destroy\n";
    }
};

Widget first;
Widget second = std::move(first); // prints: member copy
```

The destructor prevents an implicit `Widget(Widget&&)`. The generated copy constructor remains viable because its `const Widget&` parameter can bind to the xvalue.

If the destructor is genuinely required and memberwise operations are correct, state the intended operations:

```cpp
struct Widget {
    Trace trace;

    Widget() = default;
    Widget(const Widget&) = default;
    Widget& operator=(const Widget&) = default;
    Widget(Widget&&) noexcept = default;
    Widget& operator=(Widget&&) noexcept = default;

    ~Widget() {
        std::cout << "destroy\n";
    }
};
```

Defaulted moves are conditionally `noexcept`: they are non-throwing when every selected base and member move is non-throwing.

**Rule.** A type that manages no resource directly should declare none of the five special members. This rule of zero preserves copying, moving, destruction, and exception specifications automatically.

Move-only types deliberately fail in code that requires copying. Standard containers support move-only elements; their exact requirements appear in Chapter 10.

## noexcept moves and the copy fallback

Container growth must preserve existing values if an operation fails. Suppose a vector moved three old elements into new storage and the fourth move threw after modifying its source. The original range would already be partly moved from, so restoring the pre-operation state could be impossible.

`std::vector` therefore prefers a copy during reallocation when copying is available and moving might throw. The library expresses that choice with `std::move_if_noexcept`, which produces an xvalue for a non-throwing move or for a noncopyable type, and otherwise produces a `const` lvalue that selects copying.

The difference is observable without relying on capacity-growth formulas:

```cpp
#include <iostream>
#include <vector>

struct MayThrowMove {
    MayThrowMove() = default;
    MayThrowMove(const MayThrowMove&) {
        std::cout << "copy-ctor\n";
    }
    MayThrowMove(MayThrowMove&&) {
        std::cout << "move-ctor\n";
    }
};

struct NoexceptMove {
    NoexceptMove() = default;
    NoexceptMove(const NoexceptMove&) {
        std::cout << "copy-ctor\n";
    }
    NoexceptMove(NoexceptMove&&) noexcept {
        std::cout << "move-ctor\n";
    }
};

int main() {
    std::vector<MayThrowMove> cautious;
    cautious.reserve(2);
    cautious.emplace_back();
    cautious.emplace_back();
    cautious.emplace_back(); // prints: copy-ctor twice

    std::vector<NoexceptMove> fast;
    fast.reserve(2);
    fast.emplace_back();
    fast.emplace_back();
    fast.emplace_back();     // prints: move-ctor twice
}
```

`reserve(2)` makes the third insertion require new storage while avoiding any claim about a vector's growth factor. The first vector copies its two existing elements. The second transfers them.

| Element operations available | Reallocation behavior |
|---|---|
| `noexcept` move | Move existing elements |
| Potentially throwing move and copy | Copy existing elements |
| Copy but no move | Copy existing elements |
| Potentially throwing move but no copy | Move; strong guarantee may be waived |
| Neither move nor copy | Operation is ill-formed |

Defaulted moves acquire the correct `noexcept` specification from their members. If hand-written move code only swaps values or transfers handles, mark both move operations `noexcept`. Conditional `noexcept` lets generic wrappers mirror their contained operation; Chapter 20 develops that machinery.

**Pitfall.** Forgetting `noexcept` on a hand-written move can turn each vector reallocation into full element copies. For heap-owning elements, that means additional allocations and linear data movement.

Use these defaults unless a type's ownership rules require something else:

- Follow the rule of zero whenever member types already manage the resources.
- Default special members when their memberwise behavior is correct.
- Mark hand-written move construction and move assignment `noexcept` when they cannot throw.
- Delete copying for a unique-resource owner.
- Do not apply `std::move` to an ordinary local return.
- Accept a sink parameter by value, then move from it into storage.

## Latency Lens

- Moving a heap-owning type is normally a few pointer-sized transfers; copying it adds an allocation and `O(n)` element copies.
- Moving a scalar-only type performs the same data transfer as copying; keep such types simple and, where appropriate, trivially copyable (Chapter 16).
- `std::move` generates no instructions; a `const` source or missing move operation can still make the selected constructor copy.
- Guaranteed elision constructs prvalue results in caller-provided storage; `return std::move(local)` replaces a possible zero-operation handoff with a move.
- A potentially throwing move makes vector growth copy existing elements when copying is available, adding allocation and data-movement work inside the growth path.
- Moved-from objects still run destructors; even one with no resource left executes its destruction path when its lifetime ends.
- An existing xvalue passed to a by-value sink costs one move, while a same-type prvalue constructs the parameter directly; taking `const&` and then storing performs a full copy.
